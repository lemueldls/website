Every programmer eventually collides with the limitations of their type system. If you write
TypeScript, you have likely found yourself using runtime validation libraries like
[Zod](https://zod.dev/) to ensure an incoming network integer is actually positive or falls within a
specific range. If you write Rust, you might wrap a primitive integer in a custom tuple struct and
expose a constructor that returns a `Result`{lang="rust"}, ensuring your invariants cannot be
violated down the line.

Both patterns work, but they draw a sharp boundary line between compile-time checking and runtime
verification. We end up spending runtime cycles asserting facts that we feel our code should already
clearly state.

On the other end of the spectrum sit formal verification environments like Rocq and Lean. You can
prove absolute mathematical correctness about your algorithms with them. But they live in a separate
ecosystem, and working there means behaving more like a mathematician proving theorems than a
developer writing application logic.

I wanted a middle ground, so I started building **LMT** (pronounced _limit_), short for the
**Language of Meaning & Types**. It's a proof-oriented spec and meta-programming language where
types and values live in the same logical space. The goal: describe invariants, preconditions,
postconditions, and synthesis objectives right next to ordinary code, and have the compiler resolve
them at compile time.

## Types as Sets, Values as Singletons

In traditional programming languages, a type is a classification of data and a value is an instance
of it. LMT collapses that distinction: types are sets, and individual values are singleton sets
containing one element.

With types as sets, type checking becomes a question of set inclusion. If $A$ is a subtype of $B$,
the set for $A$ is a subset of the set for $B$ ($A \subseteq B$). The top type, holding all possible
values, is `Any`{lang="lmt"}. The bottom type is the empty set: `Never`{lang="lmt"} (or
`!`{lang="lmt"}).

For real programs this model only gets you so far, so LMT leans on **refinement types**. A
refinement type pairs a base type with a logical predicate that restricts its domain. Here is how
you write them in LMT:

```lmt
// Define types by refining existing ones
let Positive = Int | it > 0
let SmallEven = Int | it > 0 and it < 20 and it mod 2 == 0

// Normal type checking
let x: Positive = 7

// Explicit verification ascription
let y = 12 :: SmallEven
```

The variable `it`{lang="lmt"} is a built-in identifier that refers to the value being checked. In
the example above, `x`{lang="lmt"} is checked structurally against `Positive`{lang="lmt"}. The
`y`{lang="lmt"} assignment uses a dedicated verification ascription operator (`::`{lang="lmt"}).
This tells the compiler that a proof obligation must be formally verified right at that point before
compilation can succeed.

Subtyping between two refined types requires proving that the premise of the first predicate
logically implies the second within the current typing context.

::callout{icon="i-material-symbols:asterisk" color="info"}

Let a refined type be represented generally as $\{x: B \mid P(x)\}$, where $B$ is a base type and
$P$ is a boolean predicate. The standard subtyping judgment in a typing environment $\Gamma$ can be
formalized as:

$$
\frac{\Gamma \vdash B_1 \leq B_2 \quad \Gamma, x: B_1 \models P_1(x) \implies P_2(x)}{\Gamma \vdash \{x: B_1 \mid P_1(x)\} \leq \{x: B_2 \mid P_2(x)\}}
$$

::

In LMT's core engine, this means that subtyping checking cannot be done entirely via structural
induction over type trees. The compiler must extract the predicates, substitute the variables
appropriately, and hand the resulting implication formula over to a constraint solver to evaluate
its validity.

## Shifting the Burden to the Machine

If type checking requires proving logical implications, how does the compiler avoid getting stuck in
infinite loops or demanding that the developer manually write out mathematical proofs? It delegates
the work to an **SMT (Satisfiability Modulo Theories) solver**.

An SMT solver checks whether a mathematical formula is satisfiable within a specific theory:
integers, bit-vectors, arrays, strings, that sort of thing. When the LMT compiler type-checks an
assignment, it translates the environment's assumptions and the type predicates into SMT-LIB2, the
standard format solvers speak.

Imagine we have the following code:

```lmt
let AbsoluteInt = Int | it >= 0

let double(n: Int | it > 5): AbsoluteInt = {
    n * 2
}
```

To verify that the body of `double`{lang="lmt"} satisfies the return type `AbsoluteInt`{lang="lmt"},
the type checker generates a verification condition (VC). It collects the precondition as an
assumption and tries to prove the postcondition:

$$
\text{Assumption: } n > 5
$$

$$
\text{Goal: } (n \cdot 2) \geq 0
$$

The compiler translates the negation of the goal along with the assumptions into a formula for the
solver:

$$
\text{Formula: } (n > 5) \land \neg((n \cdot 2) \geq 0)
$$

If the solver finds the formula **unsatisfiable** (UNSAT), no integer $n$ can satisfy the
assumptions and violate the postcondition. The code is safe, in the mathematical sense. If the
formula is **satisfiable** (SAT), the invariant can be broken, and the solver hands back a
counterexample we turn into a clear compilation error.

Hand arbitrary, unguided expressions to an SMT solver and it slows down fast. To keep verification
predictable, LMT uses a **bidirectional type system** with two operational modes: _synthesis mode_
and _checking mode_.

- **Synthesis Mode ($\Gamma \vdash e \Rightarrow T$):** The compiler looks at the structural
  properties of an expression $e$ and infers its most precise type $T$. For instance, a literal
  integer `5`{lang="lmt"} synthesizes the singleton type representing exactly the value 5.
- **Checking Mode ($\Gamma \vdash e \Leftarrow T$):** The compiler is given an expression $e$ and an
  expected type $T$. It uses the shape of $T$ to guide the checking process, pushing down refinement
  conditions and wrapping the terminal leaves of the expression in verification obligations.

::callout{icon="i-material-symbols:asterisk" color="primary"}

The solver never has to discover types from scratch. The bidirectional pass pins down exactly where
verification conditions get generated, which keeps formulas small and round trips fast.

::

## Asking the Solver to Write the Code

Once the compiler can send logical constraints to an SMT solver, you can ask the solver to discover
missing code for you. This is program synthesis.

LMT supports two distinct kinds of "holes" in source files:

1. **The Type Hole (`?`{lang="lmt"}):** Asks the compiler to use standard bidirectional type
   inference to fill in a missing type or basic value based on structural rules.
2. **The Synthesis Hole (`??`{lang="lmt"}):** Instructs the compiler to translate the entire type
   specification and surrounding context into a Syntax-Guided Synthesis (SyGuS) problem, delegating
   the search for a valid implementation directly to the solver backend.

```lmt
// A type hole can infer standard structural assignments
let target = Int | it > 10 and it < 20
let a: target = ?

// A synthesis hole searches for a value or witness that satisfies a complex constraint
let square(n: Int) = n * n
let root: Int | square(it) == 16 = ??
```

When the compiler encounters `??`{lang="lmt"}, it analyzes the refinement constraint
($it \cdot it = 16$). Instead of checking an expression, it asks the SMT backend to find an
existential assignment ($\exists \, it \in \mathbb{I}, it \cdot it = 16$). The solver discovers the
value `4`{lang="lmt"} (or `-4`{lang="lmt"}), and the compiler can then logically insert that witness
directly into the compilation artifact.

That's what makes LMT a cross-language program synthesis engine. Define a data structure constraint
or a mathematical property a host function needs, and the compiler generates the logic that
satisfies it.

## Making Compilation Incremental

External SMT solvers are slow. If every keystroke meant re-parsing the whole codebase, regenerating
every verification condition, and restarting the solver process, the edit loop would be unusable. So
incremental computation is built into LMT's core pipeline from the start.

The parsing layer uses a strategy called _token windowing_ to break text processing into distinct,
independent regions. When you edit a specific line of code, the lexer and parser only re-evaluate
the local tokens within that window rather than re-traversing the entire source tree.

When an Abstract Syntax Tree (AST) fragment changes, the change flows through an interactive,
query-based dependency graph managed by [picante](https://github.com/bearcove/picante), which
handles memoization and dependency tracking.
