Traditional editors for Typst compiles whole documents into pages. An inline editor needs the opposite, per paragraph, at keystroke rate, while the document is still broken.

## What Typst is

Typst is a compiler for documents. You give it one source file and it gives you a PDF, an HTML page, or a
set of images. The source is markup for prose with a small expression language for everything else:
content you can call, content you can set rules on, content you can put inside other content.

```typst
#set heading(numbering: "1.")

= A note about blocks

The sequence $a_0 = 1$, $a_(n+1) = 2 a_n$ does not converge.
```

The unit of work is the document. Typst caches aggressively so that a recompile after one keystroke
reuses most of the previous one, but what you get back is a whole result every time. There is no way to
ask for the layout of a single paragraph, and there is no piece of a document you can hand the compiler
and get a meaningful answer for.

That `1.` in front of the heading is the clearest illustration. Its existence and its value are decided
by where the heading sits in the document, so knowing what that heading renders to means compiling
everything above it. The same goes for line breaks, for the font actually in scope, for a counter set
inside a table two hundred lines away. Nothing can be decided in isolation because everything is
available, which is exactly what makes the output good and the whole-document compile fast.

It is also the thing an editor has to get around.

## What an inline editor is asking for

A preview pane beside the source is the easy answer, and it is not what I want. I want the render
standing in for the source, paragraph by paragraph. Typeset output where the markup was. The moment the
caret lands in a paragraph, that paragraph shows its source again, and the render comes back when the
caret leaves.

Concretely, that asks for four things at once:

1. The rendered output of one paragraph, not of a document.
2. That output on every keystroke, in a browser, where the compiler has to run compiled to WebAssembly.
3. That output while the source is invalid, which is most of the time, because the user is midway
   through a word.
4. A caret that moves between the render and the source, in both directions, without the layout jumping.

Everything below is downstream of one move, which is making the compiler tell you which block produced
each piece of output it laid out. Get that and you can render one block at a time. Everything else is
the cost of getting it.

## One page per block

The obvious first move is to make Typst do the splitting for you. Break the note into top-level blocks,
join them with page breaks, compile once, then line the block list up against the pages that come back.
One block per page, so page $i$ is the render of block $i$.

```rust
let blocks = iter::zip(blocks, pages.iter().cloned())
    .enumerate()
    .filter_map(|(index, (block, page))| {
        let not_empty = !page.frame.items().len() > 0;

        not_empty
            .then(|| RangedRender::new(index, block, encode_frame(page.frame, pt)))
    })
    .collect::<Box<[_]>>();
```

That empty check is wrong, incidentally. `!len > 0`{lang="rust"} binds the negation first, so it is true for every
length including zero. Blocks with nothing in them make blank images, and a blank image and no image
look the same at the bottom of a note.

Each block then becomes a widget replacing its source range, and it is a widget only while no selection
overlaps that range. The caret returns and the source comes back. That rule is worth keeping.

Now the walls, in the order they arrive.

**Every block is a page.** Page width, page height, margins and headers are page properties. Give each
block its own page and every block gets the same geometry no matter what it is. Anything whose layout
depends on where it sits on the page is wrong, and that is most of what documents are for.

**The output is a picture.** Rasterize each page to an image and you throw away the text. Text is not
selectable, links are not clickable, and there is no way to show what an equation's source looks like
under the caret. Every font swap, theme change or pixel ratio change costs a fresh rasterization of
every block. Vector output fixes all of that at once, which is why the render is SVG and why the glyphs
are references into one shared definitions block rather than copies.

**The compile is all-or-nothing.** One error anywhere and the whole compile returns nothing, so the
whole note falls back to raw source. For a preview that is correct. For an editor it is fatal, because
the source is invalid most of the time. The fix is not to make the compiler more forgiving, it is to
stop needing the compile to succeed.

**The offset arithmetic runs out.** Click on a render, get a position in the compiled text, translate it
to a position in the source. That translation is subtraction while the compiled text and the source are
the same length, and it stops being true the moment a single byte is generated. To go further you have
to generate bytes, so you have to throw the arithmetic away and build a real map.

The shape survives all of that: compile once, get output keyed to source ranges, replace the source
with a widget, restore the source under the caret. Everything inside it needs replacing.

## One compile, read backwards

The way out of page-per-block is to compile the document exactly once and then read the result
backwards.

A compiled document is not an opaque blob. It is a list of pages, each page holds a frame, a frame is a
tree of items, and every text item carries the span of the syntax node that produced it. Those spans
are offsets into the source that was compiled. Walk the frames, ask each item which span it came from,
group the items by the source region that produced them, and each group is a rendered block.

This is the same machinery a language server uses for jump-to-definition and for clicking around inside
a preview. Nothing new is being invented. It is being used in the other direction, at a granularity
nobody cares about, once per keystroke.

So: compile, walk the frames, resolve each text item's span to a byte range, add the item's bounds to the
bounding box of the block that range belongs to. One bounding box per block, each holding exactly what
that block drew. Render each box to SVG and there is one render per block, from one compile.

Then the catch. A raw document's blocks are invisible in the output. A paragraph break leaves no trace
in the compiled frames, and nothing marks where a heading ended. You can ask which span an item came
from, but you cannot ask which block, because the compiler has no idea a block exists. The source has
to be rewritten so that a block is a thing the compiler can hand back.

One thing else falls out of the walk, and it breaks quietly if it is missed. Some items have no span at
all. A link's underline trails the text it belongs to and a list marker leads the next item, so the layout
places both outside the span of the thing they decorate. Those get held aside and attached to the first
block whose drawn content they overlap, or the underline lands in nothing and vanishes. Content pulled in
from another file has no block of its own either, so it gets folded into the block that has nothing else.

## The synth

The source gets rewritten so that every top-level block is an explicit box.

```typst
#block(stroke:0pt,width:100%)[Hello, *world*.
]
```

A paragraph becomes a block with no stroke and full width, and the paragraph's text is its content. The
compiled output of that block is a frame whose bounds are exactly the paragraph's drawn content. Nothing
else contributed to it and nothing else can land in it.

Every top-level block gets one. List items, enum items and term items do not, because boxing them
changes how they sit next to their siblings. Labels do not either. Those are copied as they are and
marked as inline.

Building the synth is a walk over the top-level nodes of the parsed tree. A node containing a newline
closes the block before it, a node without one extends it, and a block still open at the end is closed
after the walk. The case that matters most is the parser folding an unclosed raw block or a comment into
one error leaf whose text still contains newlines, because closing the previous block again at that
newline wraps it twice and produces a map whose segments run backwards. So the walk tracks the end of the
last node it accepted and stops the block there instead.

The box is invisible, and that matters twice. It does not draw, so it never appears in the render. And
its bounds are what the partition step reads, so the crop that follows has to know it is there and exclude
it.

::synth-partition{lane="synth"}

::

**Blank lines stop meaning anything.** In Typst a blank line is a paragraph break and a paragraph break
is vertical space. In an editor a blank line is a line you can put your cursor on. The synth does not
copy blank lines into the compiled text at all. They only separate blocks. The gap between blocks comes
from the box's own default spacing, which is the same 1.2em for every block no matter what is inside it.

So one blank line between two paragraphs and four of them render with the same gap. That is deliberate.
The gap belongs to the document's style, not to how many times return was pressed, and it means the
editor never has to negotiate with the compiler over how much space a blank line is worth. That
negotiation has no right answer.

**One compile covers the document.** Because each block is its own box, the partition can say which
compiled items belong to which block, and the editor renders each block on its own. Two hundred
paragraphs is one compile, not two hundred. The page-per-block approach also compiles once, but it has to
cut the document apart to read the result, and that is what destroys the geometry.

**The box costs thirty bytes of prefix and two of suffix, and they are generated.** Not typed. So the
compiled text and the user's text are two texts describing the same document, and every position that
travels between them needs a map. That is the price, and the rest of this is mostly paying it.

::callout{icon="i-material-symbols:asterisk" color="accent"}

Wrap every top-level block in an invisible box and one compile produces one render per block. The box is
what makes a block addressable, and its generated bytes are why a map has to exist.

::

## The map

The map is a tiled, bidirectional mapping between the user's text and the compiled text.

The model is a segment list. The compiled text is covered end to end by segments, and each segment says
either that this range came from that range of the source, or that this range was inserted at that source
position and came from nowhere. Segments carry a kind, which is a label and nothing more, because the map
moves bytes and does not care why a byte is there.

Mapping in one direction takes a side, and the two sides answer different questions. A start goes after
the generated bytes that precede it, so the box's opening is not part of the block. An end goes before
the generated bytes that follow it, so the closing is not either. Get it backwards and a caret placed
after a paragraph lands inside the box, which is a position that does not exist in the user's document,
and every offset after it is wrong by thirty.

Positions inside dropped text have nowhere to go, so they clamp. A caret in a blank line lands at the
end of the block above it, which is stable and matches what a plain text editor does.

The text and the segments are built together, by one builder, so they cannot drift, and a validator runs
after every build and every recovery edit checking tiling, bounds and monotonicity. A map that quietly
stops tiling is the worst failure available, because every consumer trusts it absolutely and none of them
check.

Five documents per note, then, not two, and this is where it gets easy to go wrong.

```text
the user's text        what was typed
the repaired text      plus the closing delimiters that were inserted
the render text        what actually compiles, and what recovery rewrites
the synth text         plus the boxes, built once per change and then frozen
the IDE trace text     the synth with broken ranges replaced, same length
```

Anything the editor consumes maps all the way back to the user's text: diagnostics, chunk ranges, jump
positions. That is why the render text is the only mutable one. Repairs and error marks land there, and
the render map is rewritten to match, so coming back through it always lands on something the user
actually typed.

The synth is frozen, and that rule is what keeps every IDE feature honest. Recovery is allowed to
rewrite the render text, so if hover read the render text it would read a document that had been
rewritten to make a broken equation compile. It would describe a token that is not there. A test pins
exactly this, and it is the test worth keeping above all others.

The IDE trace text exists for a narrower reason. Resolving field access inside the compiler means tracing
values, and tracing needs a main source that compiles, which a note with error marks in it does not. So
the trace text is the synth with every marked range replaced by a valid expression of the same length:
one byte becomes a zero, five bytes become three spaces. Same length, so every offset still holds. A query
landing inside a marked range reads the synth, where the token under the cursor actually lives. A query
anywhere else reads the trace text, which compiles, so tracing works.

With no repairs the whole apparatus collapses to two texts, and most keystrokes are in that state. The map
is only expensive when something is broken, which is exactly when it cannot be wrong.

## The document is broken most of the time

The user is typing. The source is invalid. That is the normal state, and the design assumes it.

The failure that defines this section: an unclosed delimiter makes the parser swallow the rest of the
document and fail with an unclosed delimiter error, no matter how many blocks get blanked. Blanking the
block that holds the error does not help, because the error is not in a block, it is in the parse. It also
deletes the text being written.

So delimiters get closed before the synth is built. A half-typed `$x_` becomes `$x_#none$`. An open raw
block gets closed. Ten constructions get this treatment.

| What is open    | What gets inserted    | Bytes |
| :-------------- | :-------------------- | ----: |
| math equation   | `$`                   |     1 |
| math string     | `"`                   |     1 |
| math attachment | `#none`               |     5 |
| raw text        | `` ` ``               |     1 |
| raw block       | ` ``` ` and a newline |    4+ |
| code block      | `}`                   |     1 |
| content block   | `]`                   |     1 |
| grouping        | `)`                   |     1 |
| code string     | `"`                   |     1 |
| block comment   | `*/`                  |     2 |

Where the closer lands is the decision that matters. It goes at the first blank line inside the
construct, or at the end of the construct if there is none. Blank lines are the boundary that was meant.
Someone typing an open `$`{lang="typst"} at the end of a paragraph, then a blank line, then another paragraph, did not
mean for the second paragraph to sit inside the equation.

Nested closers come out inner-first. `#f(1, [hello`{lang="typst"} becomes `#f(1, [hello])`{lang="typst"}, because the walk visits
children before parents and the insertions at one offset keep their order. Close the outer paren first
and the bracket is still open, which is worse than leaving both open.

A quote inside math that lands just before the user's own `$`{lang="typst"} closes both the string and the
equation, so it has to go before the `$`{lang="typst"} rather than at it.

Attachments are their own case, and the naive fix is worse than the bug. `x_`{lang="typst"} has no subscript argument,
so the parser eats the next token as the argument. In `abs((x_))`{lang="typst"} that token is the closing paren, the
nesting breaks, and the equation fails with an unclosed delimiter error, which block removal then deletes
entirely. So the attachment gets an explicit `#none`{lang="typst"} argument, which attaches nothing and leaves the
paren where it belongs.

::callout{icon="i-material-symbols:asterisk" color="warning"}

Do not blank the block holding a parse error. Blanking it deletes the text being written and it does not
fix the parse either, because the error is not in a block. Close the delimiter instead, then tell the
user it was closed.

::

::delimiter-repair{preset="content"}

::

What comes back is one warning per repair, saying what was inserted and where. Without them the repair is
invisible and the user has no idea why the document suddenly works. With them the user learns they left
something open, which is the actual lesson. The warnings use the user's own coordinates, so they
underline the character that was typed, not the byte that was inserted for it.

The repairs do not have to be the same length. Something else does, and it comes up in the next section.

## When it still doesn't compile

Repair handles open delimiters. It does not handle unknown functions, missing variables, or package
code that fails. Those still fail, and then recovery runs.

Recovery has three strategies, applied in order of specificity, in a loop that runs until the compile
succeeds or diverges after five attempts.

**Mark the math.** An error inside an equation does not get blanked. The offending token gets wrapped in
red text so the rest of the equation still lays out and the mistake is visible in context.

The naive version of that loops forever, and the reason is a good picture of what the whole system is up
against. The wrapper puts the token inside a content block, and inside a content block markup characters
are syntax again. An underscore stops being an underscore token and becomes an emphasis marker, so the
wrapper fails the same compile the unmarked text did. The fix is to swap markup-significant bytes for a
placeholder of the same byte count: hash, dollar, underscore, asterisk, backtick, tilde, angle brackets,
at-sign, backslash, brackets. An equation that fails as `$S(_)$`{lang="typst"} gets marked as `$S(?)$`{lang="typst"}, the mark
compiles, the user sees red, and the user's own bytes are still sitting in the synth where the compiler's
IDE tooling can read them.

**Blank the block.** An error outside math removes the whole block from the render text. The range used
is the outer one, box and separator included, so the block disappears completely instead of leaving an
empty box behind. The replacement is spaces plus a newline, and an empty range is refused outright,
because writing a newline into an empty range inserts a byte and shifts every offset after it.

**Bisect for the unblamable.** Some errors have no span in the note at all. Package code that fails
after layout defers to a context, so a call inside a layout block reports a span inside the package file
and no range in the note matches it. For those, recovery compiles prefixes of the block list and binary
searches for the smallest prefix that still fails. The budget is thirty-two probes, and if the prefix with
every block blanked still fails, this strategy gives up, which also rules out a failure in the prelude.
Once a block is blamed, the diagnostic is reported on its raw range, narrowed to the block's only call
expression when it has exactly one, so `#render("digraph { a -> }")`{lang="typst"} underlines the call and not
the paragraph around it.

A document with red marks in it does not compile, so it cannot be the document the IDE traces, but the
marked blocks are the ones worth looking at. So recovery renders twice. The marked pass produces the
blocks with the red marks in them. Then each mark's range is replaced with a same-length placeholder and
the document is compiled again, producing a document that hover and jump can read. The marks are what you
look at, the placeholders are what you navigate, and the raw ranges recorded next to each mark are what
connect them.

::callout{icon="i-material-symbols:asterisk" color="info"}

Recovery never touches the frozen synth. That one rule is what keeps hover, completion and jump honest,
because a document rewritten to make a broken equation compile is not the document the user typed, and
every IDE feature would be describing a token that does not exist.

::

## Making it feel like an editor

At this point each block has a bounding box and the compiled items inside it. A bounding box, though, is
not a widget height.

The editor's line box is not the font's box. The editor's line height is 1.4 times the text size,
because that is what the theme sets on the scroller. Text items come with ascender and descender metrics
straight from the font, and the two do not agree. Size a block to its drawn bounds and a single-line
paragraph comes out shorter than the line it replaces, and the text lurches every time a widget is built
or destroyed.

So text blocks get cropped to the editor's line box instead. The top is the first baseline minus the
ascender and half-leading, the bottom is the last baseline plus the descender and half-leading, where
half-leading is the difference between the line box and the font's own box, taken from the same metrics.

$$
\text{half} = \frac{1.4\,s - (a - d)}{2}
$$

The line height ratio is a shared setting, so the render and the source agree on what a line is, and
wrapped lines inside a paragraph use the editor's stride too. Change the editor's line height and the
engine's ratio has to move with it.

The crop is clamped to drawn content so tall math never clips, and only things that draw count. Text,
images, groups and filled or stroked shapes clamp the top. Links and tags do not, and the invisible box
does not, because none of them paint.

Math blocks keep their own box entirely. Extending math to the line box would change equation spacing,
which is the one thing an editor must not do to its own equations.

Then the case the whole design exists for. The cursor is inside a block, so that block shows source. The
source is one line tall and the render is four lines tall, and without help the pane lurches when the
caret enters and leaves. So the last line of the block's source range gets a minimum height equal to the
render's height minus the measured heights of the lines above it, and the layout is stable in both
directions.

That measurement has its own trap. The pass that shows a block's source runs while the block's widget is
still mounted, so asking for the line's height reports the widget's height and the number comes out as
zero. So the decorations are built first, a measurement is scheduled, the real heights are read, and a
second pass rebuilds the decorations with the correct numbers. Every dispatch the render layer makes is
effect-only, so none of it lands on the undo stack.

::callout{icon="i-material-symbols:asterisk" color="accent"}

Crop a text block to the editor's line box, not to what it drew. The difference is half-leading, and
getting it wrong makes the text lurch on every widget build. The editor's line height and the engine's
ratio are the same number in two codebases.

::

## What the user actually edits

The user edits source. That is the whole answer, and it is worth being explicit about why.

Rendered content is not selectable. It has no editable surface. Clicking it does not select it, it maps
the click back into the source: find the item under the pointer, translate its span into a position in
the user's text, and put the caret there. Alt-click on a link puts the caret in the link's source instead
of following the link. Blur the editor and every block renders, which is why a read-only pane shows the
whole document.

So the document, at every instant, is exactly what was typed. No hidden mirror, no synchronization step,
no way to drift. Undo restores text. Composition works because it happens in a real text field.
Spellchecking works because the linter sees plain document text. The CRDT mirror works because there is
one text and it is the source. Copy, paste, search and replace are the browser's own.

The cost is that the render is not directly editable. Dragging a table by its border or resizing an image
by its corner needs a source edit built for it. There isn't one.

::synth-partition{lane="laid"}

::

Click a rendered block above and the caret moves to the start of its source. Click in the source and the
block you touched goes back to text with the render's height held open underneath it. That switch, on
every selection change, is the whole interaction model.

## The keystroke budget

All of it has to happen between two keystrokes. Here is what it costs.

The trigger is a microtask, not a debounce. The pass runs on a document change, a selection change, a
focus change, a forced recompile and a geometry change. A debounce would make the render feel like a
preview. Selections are included because the popup for the equation under the caret has to rebuild, so a
selection-only pass still compiles, and the compile is caret-aware for exactly that reason.

One parse instead of four is the cheapest win. Highlighting, the delimiter repair, the synth build and
the second synth build each called the parser, and the editor also redecorates on selection changes, so
moving the cursor re-parsed the note up to four times. They share one cached parse, keyed by the text
itself, because a syntax tree says nothing about which bytes produced it.

The span index is the expensive win. A frame walk asks for two spans per text item, and resolving a span
means searching the syntax tree from the root. At 1200 blocks that is 5336 searches of a 50 KB source on
every keystroke, 28.7 ms, and the total grows with the square of the note. The index walks each compiled
source once per walk and answers from a hash map in 1.7 ms. It is dropped at the top of each successful
walk rather than on every change, because recovery rewrites the render text between walks, and although
its edits are the same length so offsets survive, an edit still renumbers the tree.

Shared definitions are the payload win, and the largest in absolute terms. An SVG exporter writes a
private definitions block into every frame, so a prose note serializes the same glyph outline once per
block that uses it. On a six-block note: 78 copies, 18 unique, so 77% of the payload is duplicated. A
300-block note goes from 6.48 MB to 1.18 MB. A 3000-block note costs 45 MB of markup where about 8 MB is
real content.

The soundness rests on the exporter naming every definition by a hash of font, glyph and scale, so an id
means exactly one outline and two frames agreeing on an id cannot disagree about its contents. That is
what makes one shared block safe for the whole app rather than per document. Two things stay out of it.
Equation popups, whose glyphs need not be in the frame set they were rendered from, because an older
frame set leaves them blank. And anything inside a shadow root, where a light-document definitions block
is unreachable, which is why plugin surfaces and the export path stay self-contained.

Three caches keep the DOM quiet. Compiled results are cached by path, engine revision and app revision,
holding two entries, so switching between two notes recompiles neither. Frame DOM containers are cached
by render hash, holding 128, and a container is reused while it is still connected. The compiler's own
SVG export is memoized, and switching workspace clears its global caches so memory does not grow.

## The ordering

An inline editor for a batch compiler comes down to an ordering. Structure the source first, so blocks are
things that can be identified. Map coordinates second, so nothing crosses a boundary unlabeled. Repair
third, so the compile has a chance. Recover fourth, so a failure is a local decision. Measure last, so it
is obvious which of the first four can be afforded.

Every attempt in another order ends in a map that cannot be debugged. The map is the product, and the
render is just its most visible output.

## Where it lives

Everything described here is real code, in two repositories. The engine that compiles Typst to WebAssembly
and hands back per-block renders, and the editor that turns those renders into widgets, live in
[typbase](https://github.com/lemueldls/typbase), a note-taking app built around the Typst language.
[Mnemo](https://github.com/lemueldls/mnemo) is the app this was first built for, and its editor is the
one that shipped all of the mistakes described above.
