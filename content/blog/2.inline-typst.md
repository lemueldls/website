Mnemo's editor has no preview pane. There's no split view and no render button. You type Typst, and
the second your cursor leaves a paragraph, that paragraph turns into the document it describes.
Click back into it and it's plain text again, cursor and all.

People who use it usually assume there's a clever trick swapping a canvas for a textarea underneath.
There is, sort of. But that part isn't actually hard.

What's hard is that Typst wants a complete, valid document before it'll compile anything, and it
stops at the first thing that's wrong. An editor that renders live has the opposite problem. The
document is basically always broken, because you're always mid-keystroke on something. Half of what
you type used to be a syntax error a tenth of a second ago.

This is the story of how that gets reconciled. It starts with the version I got wrong first.

## Chapter Zero: How It Used to Work

The renderer today compiles a note once, then figures out where everything goes. The first version
didn't trust itself to do that. It compiled the note over and over, a little more each time, and
watched what changed in between.

### A Document, Compiled One Paragraph at a Time

The old renderer lived in a file called `blocks.rs`. I'll get to why that's past tense in a minute.
It worked through a note's top-level blocks one at a time. For each block, it appended that block's
compiled text to the end of a source it had been building up, then recompiled the entire thing from
scratch.

```rust
let source = context.main_source_mut(&mut state.world)?;
let source_len = source.text().len();
source.edit(source_len..source_len, ir.get(source_len..end_byte)?);

let compiled = compile::<PagedDocument>(&state.world);
```

Then it measured how much taller the page got compared to the previous pass, and called that number
the block's height.

Picture a note with thirty paragraphs. Opening it meant running the Typst compiler thirty separate
times. Not thirty incremental passes either. Thirty full compiles, each one re-laying out everything
before it, just to answer one question: how tall did the page get this time? It's a strange way to
find a page break. It also looked completely reasonable while I was writing it, and only became
obviously strange once I'd shipped it and watched a laptop fan spin up over a grocery list.

There's a small fossil from this era still sitting in the diff, on the line deciding where an inline
block's content actually ends.

```rust
let mut end_byte = context.map_aux_to_main(aux_range.end);
if block.is_inline {
    // TODO: proper offsetting (?)
    end_byte += 29;
}
```

Twenty-nine bytes. Not a named constant, not a computed offset. Just twenty-nine, with a comment
confessing, politely, that nobody was sure this was right. I don't remember exactly how I landed on
that number. I remember it working on the documents I happened to be testing with at the time, which
is the kind of sentence that should worry you. It worried me too, eventually.

### Cropping a Painting Instead of Drawing a Sketch

The other big difference: this version didn't produce vector output at all. It rasterized the entire
merged document to one canvas, once per block, then cut a rectangle out of that canvas for the block
it currently cared about.

```rust
let canvas = typst_render::render_merged(document, context.pixel_per_pt, Abs::zero(), None);
let rect = IntRect::from_xywh(
    0,
    (y_offset as f32 * context.pixel_per_pt).ceil() as i32,
    width,
    (height as f32 * context.pixel_per_pt).ceil() as u32,
)?;
let canvas = canvas.clone_rect(rect)?;
let encoding = canvas.encode_png().ok()?;
```

Every block carried a fixed pixel ratio with it, baked into the bitmap at the moment it was drawn.
Plug a laptop into an external monitor with a different pixel density, and every rendered block had
to be thrown away and redrawn, because the bitmap that already existed was the wrong resolution for
the new screen. Vector output sidesteps this. An SVG doesn't commit to a resolution until something
downstream actually paints it, so the same markup looks right whether it lands at 1x or at 3x.

That `pixel_per_pt` field doesn't exist on `SourceContext` anymore. The dependency that made it
possible is gone too. `typst-render` is commented out in `Cargo.toml` today, right next to
`typst-pdf`, both crossed off like ingredients for a meal nobody's cooking. `blocks.rs` is still
sitting in the repository, but `pub mod blocks;` is commented out in `paged/mod.rs`. About as close
as a Rust codebase gets to a headstone.

### The Cache That Never Had a Chance

What actually killed this design wasn't the magic number, and it wasn't the rasterization. It was
that none of it could be cached. Once I understood why, the rest of the design came apart on its
own.

Caching a function's output only works if its inputs mean something stable on their own. Here, the
unit of work per block was "the compiled state of the entire document up to and including this
block", produced by mutating one shared source object inside a loop. There's no clean box you can
draw around that and say: given exactly this, you'll always get exactly that. Every block's render
depended on the accumulated side effects of every block before it. Not a value you could hash and
compare. A history.

Say you tried to cache it anyway. The cache key would have to be something like "all the text from
the start of the document up to this point." Change one character in paragraph two, and every cache
entry for paragraph three onward goes stale at once, even though paragraphs three through thirty
never changed. That's the one workload that actually matters for an editor: someone typing into a
single paragraph while the rest of the document sits still. The cache would have been useless for
exactly the thing it needed to be useful for.

I knew the new renderer needed two things this one didn't have. A render unit that was an actual
value, not a snapshot of mutable state. And a cache built by people who understood incremental
compilation, because I clearly didn't, not yet. Both of those point at the same place, which means
it's time to explain how a note's text gets from your keyboard into a compiled document at all.

## The Manuscript and the Galley

Every note in Mnemo is secretly two Typst files. The code names them `aux_id` and `main_id`, which
are fine names if you already know what they mean and useless if you don't. So here's what I
actually call them.

The **manuscript** is exactly what you typed. Nothing added, nothing removed. It's the editor's
source of truth, and it's the coordinate system that cursor positions, hover ranges, and diagnostics
get expressed in.

The **galley** is a synthesized file rebuilt from the manuscript on every recompile, and it's what
actually gets handed to Typst. A galley proof, in old print shop terms, is the typeset but not yet
paginated version of a manuscript, produced for proofreading before final layout happens. Close
enough to steal.

### Two Files Pretending to Be One

Here's what that split looks like on an actual note. Say you write this:

```typst
Hello, *world*.

This is a second paragraph.
```

That's the manuscript, in full. What Typst actually compiles looks closer to this:

```typst
#let theme = (primary: rgb(43, 127, 255), ...)
#set text(fill: theme.on-background, size: 16pt, font: "Maple Mono")
#show heading.where(level: 1): set text(fill: theme.primary, size: 32pt)
...

#block(stroke: 0pt, width: 100%)[
Hello, *world*.
]

#block(stroke: 0pt, width: 100%)[
This is a second paragraph.
]
```

Everything above your own two lines is the prelude: page geometry, the current color theme injected
as variables, default heading sizes, link styling, and default strokes for shapes and tables. None
of it is something you typed, and none of it is something you'd want to type by hand at the top of
every note. It gets regenerated on basically every keystroke, which is only affordable because
`TypstState::prelude` is `comemo`-memoized and almost never produces different output between one
keystroke and the next.

Your own two paragraphs got something added too. Each one is wrapped in an explicit block. The
function responsible, `sync_source_context`, walks the manuscript's parsed syntax tree and wraps
every run of top-level content that isn't already line-structural Typst, meaning anything that isn't
a `let`, `set`, `show`, import, or comment, since none of those produce visible output on their own.
List items, enum items, and labels get tagged but left unwrapped, since boxing them would change how
they sit next to their siblings.

### Registration Marks

None of this works unless something can answer one question. This byte, in the galley, where does it
actually live in the manuscript? Diagnostics and hover text come back from Typst speaking galley
coordinates. So does click-to-jump positioning. The editor only understands manuscript coordinates.
Something has to translate between them, continuously, while the galley gets rebuilt underneath it
dozens of times a minute.

The doc comments for this translator call its anchor points "inflection points." Technically
defensible. Completely unmemorable. I'd rather call them what they actually do: **registration
marks**, after the little crosshairs a printer lines up by hand to keep two overlapping passes of
the same page aligned. That's exactly the job here. Every place the manuscript-to-galley transform
inserts or removes text, it drops a mark: a pair of numbers recording that this manuscript position
and this galley position used to be the same place.

Here's a concrete version. Say your manuscript is a single paragraph, and by the time the prelude
and the opening of its wrapping block have both been written into the galley, seventy characters
have gone by before your paragraph's first letter does. Manuscript byte 0 lands at galley byte 70.
The mark recorded is `(0, 70)`.

Now Typst reports an error somewhere inside that paragraph, at galley byte 76. There's no mark
sitting exactly on byte 76, so the lookup finds the nearest mark before it, `(0, 70)`, and does the
arithmetic. Seventy-six minus seventy is six, so the manuscript position is byte six. That's the
character the editor underlines.

Reading a mark works in the other direction too, and which direction matters. A position sitting
exactly on a mark is genuinely ambiguous. It could mean right before the wrapper got inserted, or
right after it. Diagnostics and hover want the outer edge, so they search backward for the nearest
mark and extrapolate forward. Jump-to-source from a click wants the inner content edge instead, so
it walks forward until it finds the pair of marks bracketing the position it's actually inside of.
Same sorted list of marks. Two different ways of reading it, depending on whether you're locating
something from the outside or stepping into it from the inside.

The struct is still called `IndexMapper`, and the field holding the marks is still called
`inflections`. I didn't rename the code. I just stopped saying the word out loud.

## One Compile, Then a Sort

With the manuscript-galley split and the registration marks in place, the real performance question
was never about mapping positions. `blocks.rs` already handled that fine. The real question was how
to turn one compiled galley into a set of independently cacheable chunks, without recompiling once
per chunk just to find out where the chunks are.

### Binding the Frame Tree

The current renderer compiles the galley exactly once. Typst hands back a fully laid-out document:
pages full of frames, frames full of items like text runs, shapes, images, nested groups, and
introspection tags. Instead of asking "how tall is the document if I stop here", the renderer walks
that frame tree itself and works out, per item, which range of the galley it actually came from,
using the spans Typst already attaches to glyphs and shapes.

Go back to that thirty-paragraph note from earlier. The old renderer compiled it thirty times to
find out where each paragraph started and ended. The new one compiles it once, gets back a tree of
maybe a few hundred positioned frame items, and sorts those items into thirty buckets by checking
which paragraph's manuscript range each item's source span falls inside. Items with no traceable
range of their own, mostly tags marking where invisible elements start and end, get carried forward
and folded into whichever bucket claims the next real content. No recompiling. No probing. One
compile, then a sort.

> a handful of leaf items, arrows sorting those leaves into three or four labeled paragraph buckets
> on the right.

### A Cache That Means It

Each bucket here is an actual value: a content-addressed bundle of already-positioned frame items,
independent of how the rest of the document happens to be laid out around it. That's exactly the
shape a memoizing cache wants.

```rust
#[comemo::memoize]
fn render_svg(
    items: Prehashed<VecDeque<BoundFrameItem>>,
    width: Abs,
    height: Abs,
    document_width: Abs,
) -> SvgRangedFrame {
    // ...
}
```

`items` arrives wrapped in `Prehashed`, so the cache key is a content hash of the bound frame items
themselves, not a block index and not the raw source text. Type a character in paragraph four of
that same thirty-paragraph note, and paragraphs one through three hash to exactly what they hashed
to a moment ago. `comemo` catches that before `render_svg`'s body even runs, and the previous
rendered frame comes back untouched. No canvas. No PNG to encode.

### Borrowed Tools

Worth saying directly: `comemo` isn't some general caching library I found on crates.io and bolted
onto the side of this. It's maintained by the people who build Typst, because it's the same
machinery their compiler leans on internally to avoid relaying out your whole document every time
you change one word.

`ecow` comes from the same place. It's a clone-on-write string and vector crate, `EcoVec` and
`EcoString`, and it shows up constantly in this codebase's diagnostic and syntax-tree handling.
Cloning an `EcoVec` with a thousand entries costs about the same as cloning a single pointer,
because the clone just bumps a reference count instead of copying the thousand entries. That matters
here specifically because a memoized function needs cheap inputs to compare. If checking whether
you've already computed something costs as much as computing it again, the cache isn't saving you
anything.

Reaching for `comemo` for the chunk cache wasn't grafting a second caching system onto the compiler.
It's the same vocabulary Typst already speaks for the same problem, which is most of why this took
less work than I expected.

## When the Galley Doesn't Print

Live-as-you-type editing means the galley is invalid far more often than it's valid. Every
half-finished function call, every bare `#` you just pressed, counts as a syntax error for the brief
moment before you finish typing it. A renderer that shows nothing the instant one diagnostic fires
is unusable. So a failed compile isn't treated as the end of the attempt. It's treated as a starting
point. Find what's broken, neutralize just that part, recompile, repeat, up to a limit (32 retries
in the SVG renderer, 128 in the HTML one) so a document that genuinely can't be fixed by blanking
things doesn't spin forever.

There are two granularities for "neutralize", depending on what broke. And honestly, the core idea,
find the offending range and overwrite it with whitespace, is one of the few things that survived
the `blocks.rs` era completely intact. The old renderer blanked broken blocks inline, in the middle
of producing its next raster crop. The new one does the same trick, just as a clean pass with its
own boundary.

### Cutting Whole Blocks

The coarse version, `remove_errornous_block`, works at the level of the blocks already discovered
when the galley was built. It collects the galley ranges every diagnostic, and its trace points,
resolve to, finds which blocks those ranges fall inside, and blanks them.

```rust
let whitespace = " ".repeat(byte_length.saturating_sub(1)) + "\n";
source.edit(start_byte..end_byte, &whitespace);
```

Picture typing this into a paragraph: `The meeting moved to #emhp[next week].` You've misspelled
`emph`. Typst can't resolve that function name, and the whole paragraph containing it fails to
compile. The block-cutting pass finds the diagnostic, maps it back to that paragraph's galley range,
and overwrites the paragraph with blank space of exactly the same length. Nothing else in the note
moves, because every position after that paragraph is still measured from the same byte offsets it
always was. The paragraph itself blinks out of view for as long as the typo exists, and reappears
the instant you fix `emhp` back to `emph`.

The replacement is the same length as what it replaces on purpose. The registration marks are
absolute byte offsets, so a length-preserving edit means none of them need to change.

### A Scalpel for Math

Blanking a whole block is too blunt for equations. A formula is usually one block on its own, so a
single wrong variable name anywhere in a multi-line equation would blank the entire thing while
you're still in the middle of writing it. That's exactly the flicker the rest of this system exists
to prevent.

`try_mark_errornous` works at expression granularity instead. Say you write `$ x + y_z $` and `y_z`
isn't defined anywhere. Block-cutting would blank the whole equation, including the perfectly fine
`x +` sitting right next to the broken part. Instead, the renderer finds the diagnostic, checks that
its span resolves to a math identifier (or a sibling of one, like a subscript or a field access),
and splices a wrapper around just that piece.

```rust
let marked_text = format!("#emph(text(fill:theme.error)[{original_text}])");
source.edit(main_range.clone(), &marked_text);
```

What renders is `x +` in your normal text, followed by `y_z` in red italics. The broken half is
visibly broken. The working half keeps working.

This edit isn't length-preserving, so the registration marks need adjusting to account for the
wrapper. And because the spliced markup is what actually compiles, the renderer ends up compiling
the affected block twice: once with the wrapper in place, which produces the chunk you actually see,
and once with that same range blanked to whitespace instead, which produces a stable document for
anything downstream that needs a consistent baseline, like jump-to-source. Only the second compile's
document gets kept. The first compile's chunk is what gets shown. Afterward, the galley gets
restored to the original, unwrapped text, padded to the same length, so the next keystroke starts
from a clean baseline again.

> **[Interactive]** Another good live-demo spot: typing `$x + y_z$` with an embedded editor, showing
> `y_z` turn red and italic while `x +` stays in normal math styling next to it.

## A Magnifying Glass for Formulas

Inline rendering already shows formulas live, but a formula's natural size inside a paragraph isn't
always a good size to actually read it at. A long equation wrapped across a line, sitting next to a
wall of prose, can render small enough that you can't make out individual symbols while you're
actively working on it. The fix is a second render of just that equation, shown as a popup near the
cursor.

### Riding Along Inside an Equation

This piggybacks on the same frame-binding pass that produces the inline chunks. While walking a
page's frame tree, a small tracker called `BoundFrameSink` keeps a stack of currently open Typst
tags. Whenever the top of that stack is specifically `equation`, every item bound while it's open
gets appended to a bucket dedicated to that formula, separate from whichever paragraph block it
would otherwise belong to.

```rust
pub fn process_tooltips(&mut self, block: &BoundFrameItem) {
    if let Some((name, _span)) = self.tag_stack.last() {
        if *name == "equation" {
            self.tooltips.last_mut().unwrap().push(block.clone());
        }
    }
}
```

There's a line in the real version of this function that clones a range and maps it onto itself,
doing nothing at all. I'm fairly sure I meant to transform it into something and never finished the
thought. It's harmless. I'm leaving it there as a small monument.

### Cropped to Fit

Take the equation `$ sum_(i=1)^n i $` sitting inline in a sentence. Inline, it might render at
twelve points, squeezed between two words, subscript and superscript barely legible. The formula's
own bucket gets rendered through the same memoized `render_svg` used for the inline chunks, but with
one difference: the frame width passed in is the equation's own bounding box, not the page's full
width. So the popup crops tightly around just the sum sign and its bounds, instead of stretching to
fill the column the way the inline version does.

The bucket's manuscript range gets computed the same way the inline chunks' ranges do, but padded by
one byte on each side before converting to UTF-16. That's so hovering right on the `$` delimiters
still counts as being inside the formula, instead of landing one byte outside it and missing the
popup entirely.

### Landing the Popup

These tooltip frames come back from the compile step alongside the normal render output, and live in
their own CodeMirror state field. A small view plugin watches for selection, document, and focus
changes, and on a short delay looks for the first tooltip frame whose range contains the cursor.

```ts
for (const { render, range } of tooltips) {
  if (pos >= range.start && pos <= range.end) {
    // size a floating element to render.width / render.height
  }
}
```

When one matches, the editor builds a small floating element sized to the rendered SVG, shifts it
horizontally by the negative of the frame's recorded offset so the formula lines up under the cursor
instead of under the block's left edge, and hands it to CodeMirror's tooltip system, anchored to
where that range actually sits on screen. Hover your cursor over `i=1` inside that sum, and the
popup follows you there instead of sitting fixed at the start of the equation.

---

None of these three pieces is visible by itself. Put together, they're most of what makes the editor
feel like it's just there. Text goes in, a document comes out, and the gap between what you typed
and what compiled gets absorbed somewhere you're never meant to look.

The version that did this badly taught me more than the version that does it well. Thirty full
compiles to find a page break has a way of making the actual problem obvious, even if it took me
longer than I'd like to admit before I stopped patching the symptom and started fixing the shape of
the thing underneath it.
