In recent research, I've worked on applying program synthesis to property-based testing. Using
refinement types as specifications, the goal is to synthesize generators that are both guaranteed to
satisfy a property and capable of producing any value that satisfies it.

This post covers the pieces that make this work: refinement types as specifications, the SMT solvers
that discharge the proofs, and the negated-predicate trick for completeness.

## Type-Directed Synthesis

Program synthesis is generating code from a formal specification, normally framed as a search over a
massive space of candidate programs. The space explodes combinatorially, and that explosion is the
hurdle everything else is designed around.

[Synquid](https://github.com/nadia-polikarpova/synquid) tackles it with refinement types as
specifications. A refinement type is more expressive than a plain one: it encodes the property
directly into the type, and the synthesizer uses that to guide the search toward a program that
satisfies it.

To illustrate how these types drive synthesis, consider the `replicate`{lang="synquid"} function,
which produces a list of length $n$ containing copies of $x$. The user provides a signature, and the
tool synthesizes the recursive implementation:

::code-runner

```synquid
-- Goal: n copies of x
replicate :: n: Nat -> x: a -> { List a | len v = n }
replicate = ??
```

#compiled

```synquid
-- Synthesized Implementation
replicate = \n. \x.
  if n <= 0
    then Nil
    else Cons x (replicate (dec n) x)
```

::

What makes these types work for synthesis is that they decompose a global specification into
independent sub-goals, one per program component.

### Liquid and Refinement Type Theory

Simple types, such as those found in standard ML or Haskell, tell us the "shape" of data (like an
`Int`{lang="synquid"} or `List`{lang="synquid"}). They provide a basic structure but lack the
precision to describe complex invariants, such as ensuring a list is sorted or a tree is balanced.

Refinement types attach a logical predicate to a base type. The catch: for automated checking, the
predicates have to come from decidable theories, so an SMT solver can actually handle them.

::callout{icon="i-material-symbols:asterisk" color="primary"}

A scalar refinement type is written as $\{ \nu : B \mid \psi \}$, where $\nu$ is a special value
variable representing the term itself, $\psi$ is a formula that must hold true, and $B$ is the base
type that describes the shape of the data.

::

For example, we can define a type for natural numbers (non-negative integers) in Synquid:

```synquid
-- Synquid refinement type for Natural numbers
type Nat = { Int | _v >= 0 }

-- A signature for a function that returns a Nat equal to 5
five :: { Nat | _v == 5 }
```

Refinement types earn their keep when a data structure carries representation invariants, like a
Binary Search Tree (BST):

::code-runner

```synquid
-- Binary search tree definition with refinements
data BST a where
  Empty :: BST a
  Node  :: x: a ->
    l: BST { a | _v < x } ->
    r: BST { a | x < _v } ->
    { BST a | keys _v = keys l + keys r + [x] }
-- Size of a BST (termination metric)
termination measure size :: BST a -> { Int | _v >= 0 } where
  Empty -> 0
  Node x l r -> size l + size r + 1

-- The set of all keys in a BST
measure keys :: BST a -> Set a where
  Empty -> []
  Node x l r -> keys l + keys r + [x]

-- Synthesis Goal: Insertion into a BST
insert :: x: a -> t: BST a -> { BST a | keys _v = keys t + [x] }
insert = ??
```

#compiled

```synquid
-- Synthesized Code
insert = \x. \t.
  match t with
    Empty -> Node x Empty Empty
    Node y l r ->
      if (x <= y) && (y <= x)
        then t
        else if y <= x
          then Node y l (insert x r)
          else Node y (insert x l) r
```

::

::callout{icon="i-material-symbols:asterisk" color="info"}

Refinement types extend the standard Hindley-Milner type system with predicates. Embed the
specification in the type and the machine checks your invariants for you.

::

For a type to be useful in automated synthesis, these predicates must be drawn from decidable
logics, such as the quantifier-free logic of linear integer arithmetic, arrays, and uninterpreted
functions. This subset of logic is known as "Liquid Types" (Logically Qualified Data Types), where
refinements are restricted to conjunctions of predicates from a predefined set of logical
qualifiers. That's what turns program verification into a matter of solving subtyping constraints.

## Subtyping and Environment Assumptions

Subtyping in a refinement type system is defined by logical implication. Given two scalar types
$T_1 = \{ B \mid \psi_1 \}$ and $T_2 = \{ B \mid \psi_2 \}$, the judgment $\Gamma \vdash T_1 <: T_2$
holds if the implication $\psi_1 \Rightarrow \psi_2$ is valid under the assumptions provided by the
environment $\Gamma$.

The environment $\Gamma$ contains the types of all variables in scope, which are themselves
conjoined to form the antecedent of the implication. Formally, we define the extraction function
$[[ \Gamma ]]$ as the conjunction of all path conditions and refinements of variables mentioned in
the subtyping judgment.

Pulling these assumptions out of the environment is fiddly. It has to account for scalar variables
and for path conditions derived from branch guards.

When synthesis involves datatypes, the subtyping rules must also account for the shape of the data.
Datatypes are generally considered covariant in their type parameters, meaning $D T_1 <: D T_2$ if
$T_1 <: T_2$. Refinement types for datatypes are often associated with measures, which are
uninterpreted functions that map data structures to their properties, such as the length of a list
or the height of a tree.

| Component      | Logic Theory            | Example Refinement                                                                    |
| :------------- | :---------------------- | :------------------------------------------------------------------------------------ |
| Integer Bounds | Linear Arithmetic       | $\{ \nu : \text{Int} \mid \nu \ge 0 \wedge \nu < n \}$                                |
| List Length    | Uninterpreted Functions | $\{ \text{List } \alpha \mid \text{len } \nu = n \}$                                  |
| Set Membership | Array Theory            | $\{ \text{Set } \alpha \mid x \in \text{elems } \nu \}$                               |
| Tree Balance   | Linear Arithmetic       | $\{ \text{BST } \alpha \mid \text{abs}(\text{height } l - \text{height } r) \le 1 \}$ |

### SMT Solvers and MSFOL

Formal methods lean on SMT solvers for this. A solver decides satisfiability of a formula in
Many-Sorted First Order Logic (MSFOL) modulo a set of theories.

In practice that means calling [Z3](https://github.com/Z3Prover/z3) or
[cvc5](https://github.com/cvc5/cvc5) to discharge the implications. They're the logic engine that
tells the synthesizer whether a generated code fragment satisfies its specification.

- **Satisfiability**: Finding an assignment of values to variables that makes a formula true.
- **Validity**: Proving that a formula is true for all possible assignments. Subtyping checks are
  validity checks: is it always true that $T_1$ implies $T_2$?
- **Theory Modulo**: The "Modulo Theory" part means the solver understands the rules of specific
  domains. For example, in the theory of integers, it knows that $x + 1 > x$ is always true.

### The Horn Clause Solver

Polymorphic refinement programs present a hard problem: finding the right instantiations for type
variables and the right predicates for branching conditions. Standard type inference handles this
with a least-fixpoint Horn clause solver, but synthesis can't reuse that machinery. The program is
built top-down, so sub-component requirements flow down from the goal, producing systems of
Constrained Horn Clauses (CHCs) over unknown predicates.

A Constrained Horn Clause is an implication of the form:

$$
\phi \wedge P_1(x_1) \wedge \dots \wedge P_n(x_n) \Rightarrow H
$$

where $\phi$ is a concrete formula in a decidable logic, $P_i$ are unknown predicates, and $H$ is
either a predicate unknown or a concrete formula (the "head" of the clause). If the head is $\bot$,
the clause represents a query or a goal that must be satisfied. If the head is a predicate unknown,
it represents an inductive step or a fact.

#### Fixpoint Logic in Synthesis

The semantics of Horn clause solving depends on whether one is searching for the least or greatest
model.

- **Least Fixpoint (lfp)**: Traditionally used in verification and Datalog, the lfp starts with all
  predicate unknowns as False and iteratively weakens them until all clauses are satisfied. This
  corresponds to finding the minimal set of facts that are true in a program.
- **Greatest Fixpoint (gfp)**: Synthesis requires the gfp, which starts with all predicate unknowns
  as True and iteratively strengthens them. The gfp corresponds to the weakest precondition that
  makes a program fragment correct. Finding the gfp is fundamentally more expensive than the lfp: it
  has to search the space of liquid formulas for the most general solution that satisfies the goal.

The Synquid framework uses the MUSFix solver to compute these greatest fixpoints. Unlike earlier
solvers that used exhaustive search or template-based approaches, MUSFix is designed to be
incremental. It solves constraints as they are generated during the synthesis of individual program
terms, allowing the synthesizer to backtrack immediately if a partial solution becomes
unsatisfiable.

## MUSFix and Incremental Solving

The name MUSFix comes from Minimal Unsatisfiable Subsets (MUSes). The solver's job is to find a
valuation for a predicate unknown $P$ that satisfies a set of implications. In the context of
"liquid abduction", the solver must abduce a condition that makes a program branch valid. This
involves searching for a conjunction of predicates from a set of qualifiers $Q$.

The algorithm is inspired by the MARCO framework for MUS enumeration. MARCO uses an SMT solver to
find unsatisfiable cores within a set of constraints. When a set of predicates is found to be too
weak to satisfy an implication, MUSFix identifies the "minimal" set of additional predicates
required to make the implication valid. This process is iterative: the solver maintains a current
liquid assignment $\mathcal{L}$ and strengthens it as new constraints are issued.

### Incremental Unification and Shape Discovery

The MUSFix-based type checker introduces something called "incremental unification." Traditional
Liquid Type checkers run global Hindley-Milner unification first, resolving the shape (unrefined
types) of every term before touching refinements. In synthesis, shape and refinement have to be
discovered at the same time. As the synthesizer explores different components, it may discover new
subtyping constraints that involve free type variables. MUSFix handles this by maintaining a set of
subtyping constraints and a type assignment, interleaving shape unification with refinement
strengthening.

The solving procedure takes a subtyping constraint and either decomposes it (for function or
datatype types) or converts it into a Horn constraint (for scalar types). This incremental nature is
what allows Synquid to synthesize complex auxiliary functions. For instance, when synthesizing a
sorting algorithm using a `foldr`{lang="synquid"} combinator, the solver can propagate the
requirement that the list be sorted through the higher-order argument of the fold, effectively
deriving the specification for an insertion function without user intervention.

## Methods for Property-Based Testing

Where this research lands in practice is property-based testing: sound and complete random
generators. Property-based testing, popularized by QuickCheck, checks a function against randomly
generated inputs. Writing the generators is the bottleneck, especially for data structures with real
invariants.

### Soundness and Completeness in Random Generators

A random generator is a function that produces random values of a given type. In the context of
refined types, we demand two properties:

1. **Soundness**: Every value produced by the generator must satisfy the refinement predicate. A
   generator for `Nat`{haskell} must never produce a negative number.
2. **Completeness**: Every value that satisfies the refinement predicate must have a non-zero
   probability of being generated. A generator for `BST`{haskell} must be able to produce any valid
   binary search tree, not just a subset.

QuickCheck generators lean on "generate-and-filter", using the implication operator
`==>`{lang="haskell"}. To test a property of ordered lists, you generate a random list and throw it
away if it isn't ordered. For a random list, the probability of being sorted falls off exponentially
with length, so most of the work is discarding samples. Fail to find enough valid inputs and the
tool gives up entirely.

### Generator Synthesis via Negated Predicates

A generator is sound if it only produces values satisfying the refinement, and complete if it can
produce any value satisfying the refinement.

Let's say we have a function signature that only accepts numbers from 0 to 255:

```synquid
byte :: x: { Int | _v >= 0 && _v <= 255 } -> Int
```

We can formally write this as a refinement predicate $\text{Pred}$:

$$
\text{Pred} = \{ \nu : \text{Int} \mid \nu \geq 0 \land \nu \leq 255 \}
$$

We then want to generate a function we'll call `gen_byte`{lang="synquid"}

And define the negation of the refinement as $\neg \text{Pred}$:

$$
\neg \text{Pred} = \{ \nu : \text{Int} \mid \nu \lt 0 \lor \nu \gt 255 \}
$$

$\text{Pred}$

#invalid

$\neg \text{Pred}$

::

::callout{icon="i-material-symbols:asterisk" color="primary"}

By partitioning the input space using both the predicate and its negation, the synthesizer can
construct a generation strategy where $Gen \equiv Pred$. Soundness follows from $Gen \implies Pred$,
completeness from $\neg Gen \implies \neg Pred$.

::

In practice, this is implemented by synthesizing a generator that validates its choices against a
"negated" version of the function.

Given a function `pair`{lang="synquid"} defined as taking two integers `x`{lang="synquid"} and
`y`{lang="synquid"}, where `y`{lang="synquid"} must be equal to `x + 3`{lang="synquid"}:

```synquid
pair :: x: Int -> y: { Int | _v == x + 3 } -> Int
```

We can define a version of this function signature that also checks for the opposite refinements:

```synquid
pair_not :: x: Int -> y: { Int | _v == x + 3 } -> y_not: { Int | _v != x + 3 } -> Int
```

Then, ask the synthesizer to generate a pair of integers `x_ref`{lang="synquid"} and
`y_ref`{lang="synquid"} that satisfies the original predicate while also ensuring that any value
that does not satisfy the predicate is not generated:

::code-runner

```synquid
gen_pair :: Int
gen_pair =
  let x_ref = ?? in
  let x_val = g x_ref in
  let y_ref = ?? in
  let y_val = g y_ref in
  -- Logic check against the negated predicate to ensure completeness
  let _ = pair_not x_val y_val (g_not y) in
  pair x_val y_val
```

#compiled

```synquid
-- Synthesizing a generator for pairs where y = x + 3
gen_pair =
  let x_val = g_int in
  let y_ref = g_eq (plus x_val 3) in
  let y_val = g y_ref in
  let _ = pair_not x_val y_val (g_not y_ref) in
  pair x_val y_val
```

## Where This Is Going

The workflow I'm aiming at is simple: write the refinement type, get back an implementation plus a
generator that provably only produces valid values and provably can produce any valid value. No more
hand-writing generators and hoping they cover the space.

The open question is how far the negated-predicate trick scales. Flat numeric ranges and simple
datatypes work. Recursive structures with interlocking invariants are where I'm spending my time
now, and I expect the completeness side to get harder before it gets easier.
